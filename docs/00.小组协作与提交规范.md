# 00. 小组协作与提交规范

本规范适用于公开仓库 [lyy1-1/RL-Snake](https://github.com/lyy1-1/RL-Snake)。当前项目仍在**方案确认阶段**：可以提交讨论材料和文档修订；环境、算法、训练及 Docker 工作须等待完整技术方案审核后再开始。

## 1. 如何加入项目

仓库公开后，任何人都可以阅读和克隆。**小组成员若要直接向本仓库推送任务分支**，仍需获得协作者权限：

1. 将自己的 **GitHub 用户名**发给仓库所有者 `lyy1-1`。不要发送密码或访问令牌。
2. 所有者在仓库 **Settings → Collaborators → Add people** 中发出邀请。
3. 组员登录被邀请的 GitHub 账号，接受邮件或 GitHub 通知中的邀请，取得协作者权限。[GitHub 官方邀请说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)
4. 在本机克隆仓库：

   ```bash
   git clone https://github.com/lyy1-1/RL-Snake.git
   cd RL-Snake
   ```

HTTPS 推送需要 GitHub 认证；可使用 `gh auth login`、Git Credential Manager 或自己配置的 SSH。GitHub 不接受账号密码直接作为 Git 推送凭据。[GitHub 官方认证说明](https://docs.github.com/en/get-started/git-basics/why-is-git-always-asking-for-my-credentials)

如果公开仓库仍显示 `Repository not found`，检查仓库地址和网络连接；如果可以克隆却不能推送，检查协作者邀请及当前认证账号。没有写权限的贡献者可 fork 仓库，在自己的 fork 中创建分支并向本仓库 `main` 发起 PR。[GitHub 官方 fork PR 说明](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request-from-a-fork)

## 2. 文档与决策约定

- 先读 [项目方案决策记录](PROJECT_DECISIONS.md)。`已确认`、`待确认`、`暂定`须保持区分；讨论建议不能自行改写为最终决定。
- 论文 PDF 是主要理论依据。提交方案时写明哪些做法来自论文、哪些来自参考代码、哪些是我们自己的工程设计。
- 需要改变已确认方案时，先在 PR 中提出理由和影响，由项目负责人明确确认后再更新决策状态。
- 新增说明文档尽量使用 `00.`、`01.`、`02.` 等编号前缀，按阅读顺序排列。`PROJECT_DECISIONS.md` 保留先前指定的固定路径。
- 不提交账号密钥、`.env`、个人数据、缓存、训练日志或模型权重。仓库内容对外公开；新增第三方代码或资料前，核对其许可和来源。论文 PDF 已随仓库公开，后续资料若没有再分发许可，应改用 DOI 或官方链接。

## 3. 如何提交变更

以下命令适用于**已获得协作者权限的组员**。每项任务从最新 `main` 创建自己的分支。文档使用 `docs/主题`，后续获准开发时可使用 `feat/主题` 或 `fix/主题`。分支名使用简短英文和连字符，例如 `docs/readme-scope`。

```bash
git switch main
git pull --ff-only origin main
git switch -c docs/readme-scope
```

编辑完成后检查改动，只暂存本次任务相关文件：

```bash
git status
git diff
git add README.md
git diff --cached
git commit -m "docs: clarify project scope"
git push -u origin docs/readme-scope
```

上例中的文件路径、分支名和提交信息需要换成自己的实际改动。提交信息用一句话说明做了什么；一次提交或一次 PR 尽量只处理一个主题。不要直接推送到 `main`，也不要对 `main` 强制推送。

推送后在仓库的 **Pull requests → New pull request** 中选择 `main` 为目标分支、自己的分支为来源分支，创建 PR。[GitHub 官方 Git 工作流说明](https://docs.github.com/en/get-started/using-git/about-git)

只修改少量文字时，也可在 GitHub 网页打开文件，点击铅笔图标编辑；提交时选择**创建新分支**，再发起 PR，不要直接提交到 `main`。[GitHub 官方网页编辑说明](https://docs.github.com/en/repositories/working-with-files/managing-files/editing-files)

没有本仓库写权限的贡献者可在 GitHub 点击 **Fork**，把仓库复制到自己的账号；在 fork 的分支上提交并推送后，向 `lyy1-1/RL-Snake` 的 `main` 发起 PR。创建 PR 时检查目标仓库和目标分支，避免只把改动合并进自己的 fork。[GitHub 官方 fork PR 说明](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request-from-a-fork)

PR 描述至少写清：

- **目的与改动**：解决什么问题，改了哪些文件。
- **依据与边界**：涉及论文结论时指出 PDF 的章节或页码；说明参考代码与本项目设计的区别。
- **验证**：文档改动说明已检查的链接和内容；以后代码改动说明运行的检查及结果。
- **待确认项**：列出尚需小组或负责人决定的问题。

请至少找一位组员复核 PR；涉及方案最终决定时，还须取得项目负责人的明确确认。根据反馈继续在同一分支提交和推送，PR 会自动更新。通过复核后再合并，并删除已完成的任务分支。这里是团队约定，**不是已配置的 GitHub 分支保护规则**。

## 4. 同步其他组员的改动

开始新任务前先更新 `main`。如果自己的分支工作期间 `main` 有更新，可在自己的分支上执行：

```bash
git fetch origin
git merge origin/main
```

发生冲突时，逐个检查冲突文件，和修改同一部分的组员确认内容后再提交解决结果；不要通过覆盖他人的改动来消除冲突。
